# regen-preflight

One command that runs **every** documented regeneration in this repository
and reports which committed artifacts no longer reproduce.

Standard library only. No network. Nothing is written to your working tree.

## Why it exists

This repository documents three separate families of "regenerate the
committed artifact" command, and before this tool no single command ran all
three:

| Inventory | Count at HEAD | Already run by |
|---|---|---|
| `regenerable` entries in `report-freshness/manifest.json` | 4 | `report-freshness/freshness.py` |
| tools in `regression-checker/baselines.json` | 23 | `regression-checker/coverage_audit.py` |
| `<tool>/capture.sh` transcript regenerators | 11 | **nothing** |

A reviewer needed two commands to cover the first two families, and had no
way at all to check the third. Ten committed `captured_output.txt` files had
a documented producer that nothing ever re-ran. That is the gap this closes.

The counts above are printed from the tree itself in `captured_output.txt`,
not typed here from memory.

## Run it

The four forms below are shown inline rather than in a fenced block, for the
same reason `index-generator/README.md` does it for its repo-wide commands:
they are not records in `captured_output.txt` and it would be misleading to
present them as if they were. A full run regenerates 11 transcripts and 27
reports in throwaway copies and takes minutes, and running one from inside
this directory's own `capture.sh` would recurse (see Limits). What the
transcript does contain is the unit suite, the CLI contract, and a real
end-to-end run over the fixture repository.

- `python3 regenpre.py --root ..` — everything.
- `python3 regenpre.py --root .. --phase transcripts` — one family.
  Repeatable; the phases are `manifest`, `baselines`, `transcripts`.
- `python3 regenpre.py --root .. --only index-generator,readme-index` — one
  or more named tools. A name that selects nothing is refused: see below.
- `python3 regenpre.py --root .. -o preflight_report.json` — write the JSON
  report to a file instead of stdout.

Exit `0` when every item is `match` or `volatile_only`; `1` when anything is
`environment`, `drift` or `error`; `2` on a usage error.

**`--only` has to select something.** A name this repository does not offer
(a typo of a real directory is the common case), or a value that splits
into no names at all, exits `2` and names both the mistake and the names
that would have worked; so does a real name asked for in a `--phase` that
cannot select it. Until this was repaired any string was accepted, the
filter dropped every item, and the run wrote a report saying `total: 0`,
`failing: 0` and exited `0` — an authoritative green result from a run
that checked nothing. `ONLY_REJECTION_EVIDENCE.txt` records that
behaviour at the parent commit and the exit codes now.

An **empty** `--only` is deliberately not refused: it was falsy where the
filter is built, so it has always meant "no filter" and checked
everything. Rejecting it would change the findings path rather than
repair it.

## Nothing runs in your working tree

`capture.sh` rewrites its committed transcript in place, and the report
generators write files. So every regeneration runs inside a throwaway copy
of the repository, and **each transcript regeneration gets its own fresh
copy**. That second part is not paranoia: regenerating one tool's transcript
changes an input another tool's `capture.sh` reads, so sharing one copy
would make the results depend on the order they ran in.

`test_regenpre.py` asserts this directly — it hashes every file in a fixture
repository before and after a full run and requires the set of files and
their bytes to be unchanged, and separately requires that no scratch
directory survives.

## The five states

| State | Meaning | Fails the run |
|---|---|---|
| `match` | regenerated bytes identical to committed bytes | no |
| `volatile_only` | differs only in fields that are volatile by nature | no |
| `environment` | differs in a way that tracks the Python interpreter, not the repository | yes |
| `drift` | differs in some other way — the committed artifact no longer matches its producer | yes |
| `error` | the documented command could not run at all | yes |

`volatile_only` is deliberately narrow. Exactly two patterns are masked, both
named in `VOLATILE_PATTERNS` and echoed into every report so a reader can see
what was hidden:

- `unittest_duration` — `Ran <N> tests in <duration>s`. The **count is not
  masked**: two runs disagreeing on `N` is real drift and must stay visible.
- `tempdir_name` — random `tempfile` directory names that reach the output
  because a test prints an error message containing the full path.

The number of substitutions is reported per item. Masking is never silent.

`environment` is separated from `drift` on purpose, because they call for
different responses: drift means fix the artifact, environment means the
artifact is only reproducible on one interpreter and that fact should be
recorded rather than papered over.

## What a full run found at HEAD

Recorded in `preflight_report.json`. Three findings are worth naming:

**1. `regression-checker` baselines `bundle-index` on a fixture that is not
in the repository.** The baselined command is
`python3 bundle_index.py bundle_bad -o {REPORT}`, and `bundle-index/`
contains `bundle_ok/` but no `bundle_bad/`. It exits `2`,
"bundle directory 'bundle_bad' does not exist". This baseline can never
reproduce on a clean checkout — it is not stale, it is unrunnable, and
`regression-checker`'s own committed report has been carrying it as its one
`stale` entry. `regenpre` classifies it `error` rather than `drift`, which is
the distinction that tells you it is a missing fixture and not a changed
output.

**2. `env-leak-scanner`'s transcript was interpreter-locked -- and has since
been unlocked.** Its committed `captured_output.txt` used to record
`Python 3.10.12`, and unittest changed its test-id rendering in 3.11
(`test_x (mod.C)` became `test_x (mod.C.test_x)`), so that transcript could
not reproduce on a 3.11 interpreter no matter what the repository did. This
tool is what surfaced that; it had never been stated anywhere.

It was regenerated on CPython 3.11.15 as a side effect of an unrelated
repair to that directory, and the item now classifies `volatile_only`
rather than `environment`. The underlying property has not gone away -- the
transcript is now pinned to 3.11 instead of 3.10 -- but the lock now points
at the interpreter the repository is actually being run on, and the
`transcripts` phase has no `environment` items left. The finding is kept
here rather than deleted, because "we found it and it was then fixed" is
more useful to a reader than silence.

**3. The rest of the repository is in better shape than the absence of any
checker would suggest.** The full run at HEAD is 40 items:

| Phase | items | match | volatile_only | environment | error |
|---|---|---|---|---|---|
| `manifest` | 5 | 5 | 0 | 0 | 0 |
| `baselines` | 23 | 22 | 0 | 0 | 1 |
| `transcripts` | 12 | 8 | 4 | 0 | 0 |

Eight of the twelve transcripts reproduce **byte for byte**;
`env-leak-scanner`, `index-generator`, `readme-index` and `shebang-mode`
differ only in masked durations and temp-directory names. One of those
eight is this directory's own, which is reported as a skip with its reason
rather than counted as a real regeneration — see Limits. That leaves
finding 1 above as the only thing anyone needs to act on, and it is a
checkable claim rather than an assumption.

## `preflight_report.json` is committed as evidence, not as a regenerable report

It is deliberately **not** added to `report-freshness/manifest.json`, because
it would not survive the check honestly: the `environment` classification
depends on the interpreter the run happened on. That is not hypothetical --
the `env-leak-scanner` item has now been on both sides of it, `environment`
while its transcript recorded 3.10 and `volatile_only` since it was
regenerated on 3.11. A report whose content is a function of the machine
cannot be a byte-for-byte regenerable artifact, and pretending otherwise
would make `freshness.py` fail for a reason that has nothing to do with the
repository.

The committed report was produced on **CPython 3.11.15**. Anyone re-running
it on a different minor version should expect transcript items whose
recorded interpreter differs to come back `environment`.

## Limits, stated plainly

- **The `transcripts` phase excludes this directory.** `regenpre`'s own
  `capture.sh` runs `regenpre`, so regenerating its transcript from inside
  the transcripts phase would recurse. The exclusion is by directory name
  (`SELF_DIR`) and it is reported as an item with an explicit reason, not
  silently dropped from the list.
- **`volatile_only` is a judgement, not a proof.** Masking a duration means
  asserting that a duration cannot carry a real regression. That is true for
  the two patterns here, and it is the reason the mask list is short, named,
  and counted rather than a general "ignore numbers" rule.
- **`environment` detection is pattern-based**, currently the `Python
  <version>` banner and the unittest test-id shape. Another interpreter
  difference that produced neither would be classified `drift`. That is the
  safe direction: it over-reports a problem rather than explaining one away.
- A full run is minutes, not seconds, because it genuinely re-runs
  everything. There is no caching, deliberately — a cache is one more thing
  that can be stale, which is the failure mode this tool exists to catch.
