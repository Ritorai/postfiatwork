# path-collision-scanner

A stdlib-only Python 3 CLI that reads a set of repository-relative path
names — by default the Git-tracked set — and reports the ones that
**collide with each other, or break outright, on a filesystem other than
the one they were committed from**.

Every rule here describes a failure that is invisible on Linux. Two files
called `Notes.md` and `notes.md` coexist happily on ext4; on macOS or
Windows a `git checkout` writes one over the other and the working tree
silently stops matching the commit. `aux.json` cannot be created on
Windows at all. A file name ending in a space or a dot is accepted by
Linux and silently renamed by Windows. Evidence lives in files, so a
repository whose evidence quietly loses a file on the reviewer's machine
has an evidence problem, not a cosmetic one.

## Requirements

Python 3 standard library only: `argparse`, `json`, `os`, `re`,
`subprocess`, `sys`, `unicodedata`. No third-party packages, no network.
`git` is needed only for the default Git-tracked mode; `--paths-from`
works without it. Verified on CPython 3.11.15, Linux x86_64.

## Usage

```
python3 pathscan.py [--root DIR] [-o FILE] [--rules R1,R2]
python3 pathscan.py --paths-from FILE|- [-o FILE] [--rules R1,R2]
python3 pathscan.py --list-rules
```

- `--root PATH` — repository root to run `git ls-files -z` in (default `.`)
- `--paths-from PATH` — read a NUL-delimited path list instead of asking git;
  `-` reads stdin
- `-o, --output PATH` — write the report JSON here instead of stdout
- `--rules A,B` — enable only these rule ids (default: all)
- `--list-rules` — print the rule ids and exit `0`

### Exit codes

| Code | Meaning |
|---|---|
| `0` | no findings |
| `1` | findings — at least one path collides or breaks elsewhere |
| `2` | setup error: `--paths-from` missing/malformed, `git ls-files` failed, `--root` not a directory, `--output` unwritable, unknown `--rules` id |

Malformed **input** is exit `2`, not a finding. If a path list contains an
interior empty entry, the scanner cannot tell whether the producer meant a
file with an empty name or emitted a stray NUL separator, and guessing
would turn a broken pipeline into a clean report. Same for a non-UTF-8
entry. Exit `1` is reserved for paths the scanner actually understood.

## Why there is a `--paths-from` mode

The fixtures this tool needs are path *names*, and several of them cannot
be created as files on the machine that has to test it. A name containing
a newline is illegal on Windows. `aux.json` cannot exist there. Two names
differing only by case cannot coexist on macOS. A test suite built from
real directory trees would therefore be untestable on exactly the
platforms whose failures it is meant to model.

So the fixture format is a NUL-delimited path list — the same bytes
`git ls-files -z` emits — and `make_fixtures.py` writes them. NUL-delimited
because a path name may legally contain a newline, so a newline-delimited
list is ambiguous by construction; there is a fixture with a real newline
in a file name precisely to pin that down.

## Rules

| Rule id | What it catches | Where it bites |
|---|---|---|
| `CASE_FOLD_COLLISION` | two or more distinct paths whose NFC casefold is equal | macOS (default), Windows |
| `UNICODE_NORMALIZATION_COLLISION` | two or more paths with the same NFC form but different bytes (NFC vs NFD) | macOS, which stores NFD |
| `WINDOWS_RESERVED_NAME` | a component whose stem is `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9` | Windows — the file cannot be created |
| `TRAILING_DOT_OR_SPACE` | a component ending in `.` or a space | Windows silently strips it, renaming the file |
| `CONTROL_CHARACTER` | any `U+0000`–`U+001F` or `U+007F` in the path, including newline and tab | Windows rejects; every line-based tool misparses |
| `WINDOWS_ILLEGAL_CHARACTER` | `< > : " \| ? *` or a backslash inside a component | Windows — the file cannot be created |
| `UNSAFE_RELATIVE_PATH` | absolute path, drive-letter prefix, backslash separator, `.`/`..`/empty component, trailing separator | archive extraction and checkout escape the repository root |
| `DUPLICATE_PATH` | the same path appears more than once in the input list | a broken producer upstream of the scanner |

### Rules that deliberately do not double-report

- A pair that differs **only** by Unicode normalisation is
  `UNICODE_NORMALIZATION_COLLISION` and **not** `CASE_FOLD_COLLISION`,
  even though their casefolds are equal. It is one defect. A pair that
  differs by both case *and* normalisation is reported as a case
  collision, because fixing the case fixes it.
- `.` and `..` end in a dot but are reported only as
  `UNSAFE_RELATIVE_PATH`, never also as `TRAILING_DOT_OR_SPACE`.
- The colon in a `C:/…` drive prefix is **not** reported as a Windows
  illegal character; the path is already `UNSAFE_RELATIVE_PATH` for
  having the prefix. A backslash **is** reported by both rules, because
  "this is not a separator" and "this character is illegal in a name" are
  two different things to fix.
- A duplicated path is counted once for every other rule.
  `aux.txt` listed twice is one `WINDOWS_RESERVED_NAME` finding and one
  `DUPLICATE_PATH` finding, not two of each.

## Report format (canonical JSON)

```python
json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=True) + "\n"
```

Sorted keys, no extra whitespace, ASCII-only, exactly one trailing
newline. `ensure_ascii=True` matters here more than usual: a path
containing a literal newline would otherwise put a raw newline inside the
JSON string, and every downstream `grep`/`wc -l` would misread the report.

```json
{
  "schema_version": 1,
  "tool": "path-collision-scanner",
  "status": "clean" | "findings" | "error",
  "source": "git" | "path-list",
  "paths_scanned": 388,
  "distinct_paths": 388,
  "rules_enabled": ["CASE_FOLD_COLLISION", "..."],
  "summary": {"CASE_FOLD_COLLISION": 0, "...": 0},
  "findings": [
    {"rule_id": "...", "paths": ["..."], "detail": {...}}
  ]
}
```

`findings` is sorted by `(rule_id, paths)`; `paths` inside a finding is
sorted; `summary` always carries every rule id, including the zeros, so a
consumer never has to distinguish "rule found nothing" from "rule was
renamed". Input order does not affect the report — pinned by a test.

### What is deliberately NOT in the report

- **No timestamps and no durations.** They would destroy the
  byte-for-byte reproducibility that the relocation proof depends on.
- **No absolute paths that the scanner derived.** `--root`, the working
  directory, and the `--paths-from` file's own location are never written
  into the report. Paths in the report are exactly the strings that were
  scanned — so if you *feed* it absolute paths, they will appear, because
  reporting them is the finding.

## Verification (reproduced in captured_output.txt)

```
rm -rf fixtures                       # prove the fixtures are derivable
python3 -m unittest test_pathscan
python3 make_fixtures.py --check ; echo "exit=$?"
python3 pathscan.py --paths-from fixtures/clean.paths ; echo "exit=$?"
python3 pathscan.py --paths-from fixtures/dirty.paths -o d1.json ; echo "exit=$?"
python3 pathscan.py --paths-from fixtures/malformed.paths ; echo "exit=$?"
python3 pathscan.py --list-rules
```

Actual results: **95 tests, `OK`**; `make_fixtures.py --check` exit `0`;
exit codes `0`, `1`, `2` in that order.

## The real repository scan, and the relocation proof

`captured_output.txt` Part 2 contains a scan of this repository's own
tracked path set — **388 paths, `"status": "clean"`, exit `0`, every rule
zero.** That is a negative result and it is reported as one.

A clean result from a scanner is worth nothing on its own, so Part 2 also
contains a **positive control**: the same 388-path tree with a single
`README.MD` added next to the existing `README.md`. The scanner returns
exit `1` and exactly one finding,
`CASE_FOLD_COLLISION ["README.MD", "README.md"]`. The clean result above
is therefore a measurement, not a no-op.

**Relocation.** Two runs from the same directory prove nothing about path
leakage — the leak would be identical in both. The tracked tree is
therefore materialised at two *differently named* absolute paths
(`.../repoA` and `.../repoB_with_a_much_longer_name`) and scanned from
each. Both reports hash to
`454087407fd66623f0926fedc980cf94f2c5f300d8f5572d63716a835db14a90` and
`cmp` reports them byte-identical. `test_pathscan.py::TestRelocation`
pins the same property in-suite by copying the tool and its fixtures to
two differently named temp directories.

**Provenance of the 388 paths — read this before trusting the number.**
This environment has no outbound git access, so the tracked path set was
not obtained by cloning. It was read from the GitHub tree API for
`main` at commit `8f1b556c`, written to disk as 388 placeholder files, and
committed to a local `git init` repository, which is what `git ls-files -z`
then enumerated. The scanner only ever examines path *names*, so file
contents are irrelevant to the result — but the honest statement is "these
are the 388 tracked path names at `8f1b556c`, re-materialised locally",
not "this repository was cloned and scanned". The four files this commit
adds were not in that set; they are scanned by the next run of the tool.

## 3 limitations a reviewer should scrutinise

1. **`CASE_FOLD_COLLISION` uses Python's `str.casefold()`, which is not
   any real filesystem's folding table.** APFS and HFS+ fold against a
   frozen Unicode 3.2-era table; NTFS folds against a table baked into the
   volume at format time. `casefold()` follows the Unicode version of the
   running interpreter. For ASCII names — which is all 388 paths in this
   repository — they agree. For names using Cherokee, Georgian, or the
   Turkish dotted/dotless `I`, they can disagree in both directions, so
   this rule can both miss a real collision and report one that a given
   volume would tolerate. None of this has been tested on macOS or
   Windows; **no run in `captured_output.txt` happened on either.**

2. **A clean report is a statement about names, not about checkout
   behaviour.** The scanner never touches a filesystem, never creates a
   file, and never asks git what it would do. Case-insensitivity is a
   *volume* property, not an OS property — a case-sensitive APFS volume
   has no problem with `Notes.md`/`notes.md`, and `core.ignorecase`
   changes what git itself does. So a finding is "this pair would collide
   on a case-folding volume", not "this pair will break for your
   reviewer", and a reviewer on a case-sensitive volume can dismiss it.

3. **The Windows rule set is the classic Win32 one and is neither
   complete nor version-aware.** `CONIN$`, `CONOUT$` and the `\\?\`
   prefix forms are not checked. The 260-character `MAX_PATH` limit is not
   checked at all, and it is a real risk this tool does not cover: the
   longest tracked path here is 75 characters, which is comfortable, but
   the scanner would not have told me if it were 300. Long-path support
   is also opt-in per Windows installation, so a fixed limit would produce
   findings that are wrong on modern configurations — I would rather not
   ship the rule than ship one that cries wolf. Named here rather than
   left as a silent gap.

## No third-party imports check

`test_pathscan.py::TestStdlibOnlyImports` parses `pathscan.py`'s own AST
and asserts every import resolves to the fixed allow-list (`argparse`,
`json`, `os`, `re`, `subprocess`, `sys`, `unicodedata`) — enforced by a
test, not by a comment.
