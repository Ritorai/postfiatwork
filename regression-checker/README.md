# regression-checker

A stdlib-only Python 3 CLI that re-runs every tool's documented fixture
command and detects drift in **exit code** or **report bytes** versus a
committed baseline. Built for a repository of ~23 independent CLI tools
(queue-auditor, preflight, link-integrity, staleness-monitor,
wallet-reconciler, lifecycle-linter, event-linter, sybil-detector,
xrpl-auditor, evidence-scorer, xrpl-address, throughput-reporter,
budget-forecaster, schema-checker, evidence-harness, dup-detector,
evidence-manifest, reward-reconciler, reward-anomaly, consolidate,
payload-validator, loop-health, bundle-index), but the checker itself has
no knowledge of any specific tool -- everything it needs comes from
`baselines.json`.

## Requirements

Python 3 standard library only: `argparse`, `hashlib`, `json`, `os`,
`shlex`, `subprocess`, `sys`, `tempfile`. No third-party packages, no
network access. Verified on stock `python3` (CPython 3.10.12 on Linux).

## Usage

```
python3 regress.py [--root DIR] [--baselines FILE] [-o FILE] [--timeout SECONDS]
python3 regress.py --update-baselines [--root DIR] [--baselines FILE] [--timeout SECONDS]
```

- `--root PATH` -- directory containing tool subdirectories (default `.`)
- `--baselines PATH` -- baseline JSON file (default `baselines.json`)
- `-o, --output PATH` -- write the report JSON here instead of stdout
- `--timeout SECONDS` -- per-tool subprocess timeout (default `120`)
- `--update-baselines` -- **rewrites** `baselines.json` from current runs (see below)

### Exit codes

| Code | Meaning |
|---|---|
| `0` | no drift detected |
| `1` | drift detected (this includes per-tool `EXECUTION_ERROR`, see below) |
| `2` | setup error: baselines file missing/invalid, `--root` missing, `-o` unwritable |

**Why is a per-tool execution error exit `1`, not `2`?** A tool that used
to run cleanly and now times out, or whose interpreter can no longer be
found, or whose report file silently stopped being written, *is* a
regression -- exactly what this checker exists to catch. Exit `2` is
reserved for problems with the checker's **own** setup (it never got a
chance to run anything meaningful): an unreadable/malformed baselines
file, a missing `--root`, or an unwritable `--output`. Anything that goes
wrong while trying to reproduce a specific tool's command is the drift
code `EXECUTION_ERROR` and rolls into exit `1`.

## Report format (canonical JSON)

Every report -- success, drift, or setup error -- is:

```python
json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=True) + "\n"
```

Sorted keys, no extra whitespace, ASCII-only (non-ASCII is `\uXXXX`
escaped), exactly one trailing newline. Two runs against identical inputs
produce **byte-identical** output -- this is checked directly in
`captured_output.txt` (`cmp r1.json r2.json && echo BYTE-IDENTICAL`) and
in `test_regress.py`.

Drift report shape:

```json
{
  "schema_version": 2,
  "tool": "regression-checker",
  "status": "clean" | "drift",
  "tools_checked": 23,
  "summary": {"clean": 21, "drift": 2, "skipped_unbaselineable": 0},
  "drift_counts": {"ABNORMAL_TERMINATION": 0, "EXIT_CODE_DRIFT": 1, "REPORT_HASH_DRIFT": 1, "TOOL_MISSING": 0, "UNBASELINED_TOOL": 0, "EXECUTION_ERROR": 0},
  "results": [
    {"tool": "...", "status": "clean" | "drift" | "skipped_unbaselineable", "drift_codes": [...], "detail": {...}}
  ]
}
```

`results` is always sorted by tool name (tool discovery is sorted, and the
union with baseline-only names is sorted again before evaluation).

**`schema_version` is `2`.** Version 1 reports carried no information about
*how* a subprocess ended. Version 2 adds a `detail.termination` field
(`"exited"` or `"signalled"`), an accompanying `detail.signal` when
signalled, and the `ABNORMAL_TERMINATION` drift code. Any consumer that
pinned the exact key set of `detail` or of `drift_counts` will see new
keys; nothing was removed or renamed.

### Drift codes

| Code | Meaning |
|---|---|
| `EXIT_CODE_DRIFT` | the command ran, but its exit code no longer matches the baseline |
| `REPORT_HASH_DRIFT` | the command ran, but the SHA-256 of its report bytes no longer matches the baseline (a baseline entry with `expected_report_sha256: null` **always** drifts this way -- there is no known-good hash to compare against yet) |
| `TOOL_MISSING` | the baseline names a tool directory that is not present under `--root` |
| `UNBASELINED_TOOL` | a tool directory exists under `--root` with no entry in the baseline file at all -- **this is deliberate**: a checker that silently ignores new tools gives false assurance, so any directory it cannot account for is reported as drift, not skipped |
| `EXECUTION_ERROR` | the command could not be meaningfully executed: interpreter/binary not found, subprocess timed out, or (for `report_mode: "file"`) the report file was never created |
| `ABNORMAL_TERMINATION` | the process was killed by a signal rather than exiting (POSIX: `subprocess` reports this as a **negative** returncode). Raised unconditionally -- a baseline that literally records `-9` cannot bless a `SIGKILL`, because a signalled process never produced an exit status to compare against, and whatever report bytes it left behind are partial by construction |

A single tool can carry more than one drift code at once (e.g. a report
file that is never created *and* an interpreter that exits with an
unexpected code both fire together).

## What is deliberately NOT in the report

- **No durations.** Recording "how long did this take" is the obvious
  thing to bolt onto a test runner's report, and it is exactly the kind
  of field that silently destroys byte-for-byte reproducibility -- the
  entire point of hashing the report. If you need timing, wrap the
  invocation in `time python3 regress.py ...` out-of-band; it must never
  live inside the JSON.
- **No wall-clock timestamps.** Same reasoning.
- **No absolute paths.** `--root`, tool working directories, and the
  temporary files used to capture `report_mode: "file"` output are never
  written into the report. Verified directly: `grep -c "/sessions\|/tmp\|/home" r1.json` prints `0`.

## How a tool's command and report are modeled

Each baseline entry looks like:

```json
{
  "tool_name": {
    "status": "baselined",
    "command": ["python3", "tool.py", "input.json", "-o", "{REPORT}"],
    "report_mode": "file",
    "expected_exit_code": 1,
    "expected_report_sha256": "<64-hex-char sha256, or null>"
  }
}
```

- `command` is a **literal argv list**, never a shell string. `regress.py`
  calls `subprocess.run(command, cwd=tool_dir, ...)` with no shell
  involved at any point. This means a documented command that happens to
  contain shell metacharacters (`;`, `|`, `&&`, `` ` ``, `$()`, `>`) is
  passed through completely inert -- it is just another argv token to the
  child process. `fixtures/tool_shell_meta` exercises exactly this.
- `report_mode: "file"` -- the literal token `{REPORT}` in `command` is
  replaced with an absolute path inside a fresh, per-run temporary
  directory (never inside `--root`, never inside the tool's own
  directory) before the subprocess runs; after it exits, that file's
  bytes are hashed and the temp directory is deleted. If the file was
  never created, that's `EXECUTION_ERROR`, not a crash.
- `report_mode: "stdout"` -- the tool has no `-o`/report-to-file mode at
  all (e.g. `dup-detector` without `-o`); the subprocess's captured
  stdout bytes are hashed directly.
- A tool can be marked `"status": "unbaselineable"` with a required
  string `"reason"` instead of a command. It is then always
  `skipped_unbaselineable` (never drift) as long as its directory is
  present, and `TOOL_MISSING` if the directory disappears entirely.

## `--update-baselines` -- read this before you use it

```
python3 regress.py --root <repo> --baselines baselines.json --update-baselines
```

This is how a real regression gets **whitewashed**. It re-runs every
already-baselined entry and overwrites its `expected_exit_code` and
`expected_report_sha256` with whatever the tools produce right now. It
prints a loud warning banner to stderr every time it runs. It is **never**
implied by any other flag or invoked implicitly by the plain regression
check -- `test_regress.py::TestUpdateBaselines::test_update_baselines_never_runs_without_the_flag`
pins this down directly. Treat every diff it produces in `baselines.json`
as something that needs a human's sign-off before it's committed, exactly
like you would a snapshot-test update.

`--update-baselines` does **not** silently add coverage for tool
directories that have no entry at all (`UNBASELINED_TOOL` is not
"fixed" by running `--update-baselines`) -- adding a new tool to the
baseline is a deliberate, separate edit to `baselines.json`.

### What `--update-baselines` now refuses to record

The warning banner alone was not enough: the updater used to accept
*any* run that produced readable bytes and write its exit code and hash
straight into the committed baseline. That is how a crash gets frozen in
as the expected result. Three refusals now sit in front of the write, and
each one is reported as `FAILED <tool> <reason>` with overall exit `2`:

| Refusal | Why |
|---|---|
| the run was killed by a signal | its report is partial by construction; baselining it makes the crash permanently "expected" |
| the run produced a **0-byte** report | the signature of a tool that died before writing anything. Override with `--allow-empty-report` if an empty report is genuinely this tool's correct output |
| the entry's current `expected_exit_code` is a JSON boolean | the old-vs-new comparison would print `same` for a value that actually changed, because `False == 0` |

A refusal is per-entry: healthy entries in the same file are still
updated, and the failures are listed explicitly rather than skipped
quietly.

## fixtures/

**Generated, and deliberately not committed** -- the same convention as
`bundle-verifier/`, `exit-harness/` and `tamper-runner/`, which each ship a
`make_fixtures.py` and commit no generated tree. Build it with
`python3 make_fixtures.py`; `test_regress.py`'s and
`test_regress_integrity.py`'s `setUpModule()` build it automatically if it is
absent, so a fresh clone runs green with no extra step. Verify an existing tree
still matches the generator with `python3 make_fixtures.py --check` (exit `0`
match, `1` mismatch). The two baseline files are not hand-typed either: `make_fixtures.py` runs each
fixture tool the same way `regress.py` would, measures its real exit code
and the SHA-256 of its real report bytes, writes those into
`baselines_ok.json`, and then corrupts exactly one field per entry to
produce `baselines_drift.json` -- so each drift code has one unambiguous
cause. The interpreter token committed into the baselines is the literal
string `python3`, never `sys.executable`, because an absolute interpreter
path in a committed file is unreproducible on any other machine.

Seven tiny synthetic "tools" (`fixtures/tool_*`), each a few lines of
Python, used by the required VERIFICATION commands and by
`test_regress.py`'s CLI-level tests:

- `tool_ok` -- clean in both baseline files
- `tool_exit_drift` -- always exits 0; `baselines_ok.json` records the
  true value (clean), `baselines_drift.json` deliberately records the
  wrong expected exit code (`EXIT_CODE_DRIFT`)
- `tool_hash_drift` -- always produces the same report; `baselines_ok.json`
  records the true hash (clean), `baselines_drift.json` deliberately
  records a wrong-but-well-formed hash (`REPORT_HASH_DRIFT`)
- `tool_error` -- has **no** `tool.py` at all. `baselines_ok.json` marks
  it `unbaselineable` (kept out of the clean baseline); `baselines_drift.json`
  wires it up as a real (failing) command, producing `EXECUTION_ERROR`
- `tool_stdout` -- report-to-stdout mode, clean in both
- `tool_shell_meta` -- its baselined command includes a literal argv
  token full of shell metacharacters; the tool just echoes it back,
  proving `regress.py` never invokes a shell
- `tool_null_hash_demo` -- `unbaselineable` in `baselines_ok.json`;
  baselined with `"expected_report_sha256": null` in
  `baselines_drift.json`, demonstrating that a null hash always drifts
- `baselines_drift.json` additionally references `ghost_tool`, a name
  with no matching directory at all, to exercise `TOOL_MISSING`

`UNBASELINED_TOOL` and most single-function edge cases are covered instead
by `test_regress.py` building throwaway tool directories under
`tempfile.TemporaryDirectory()`, so the committed `fixtures/` tree stays
exactly the shape the VERIFICATION commands expect.

## The real baseline (`baselines.json`)

`baselines.json` was **not** hand-typed. It was built by:

1. Writing one entry per real sibling tool with its documented
   fixture command (drawn from each tool's own `README.md` /
   `RUN_COMMANDS.md` and cross-checked against its own
   `captured_output.txt`), leaving `expected_exit_code`/
   `expected_report_sha256` as placeholders.
2. Running `python3 regress.py --root <sibling-repo-root> --baselines baselines.json --update-baselines`
   once, so every value in the committed file is the actual output of
   actually executing the tool.

All 23 named tools (`budget-forecaster`, `bundle-index`, `consolidate`,
`dup-detector`, `event-linter`, `evidence-harness`, `evidence-manifest`,
`evidence-scorer`, `lifecycle-linter`, `link-integrity`, `loop-health`,
`payload-validator`, `preflight`, `queue-auditor`, `reward-anomaly`,
`reward-reconciler`, `schema-checker`, `staleness-monitor`,
`sybil-detector`, `throughput-reporter`, `wallet-reconciler`,
`xrpl-address`, `xrpl-auditor`) had a runnable, deterministic, documented
command and were successfully baselined -- **none were unbaselineable**.
Several of the derived hashes were cross-checked against the sha256sums
already committed in each tool's own `captured_output.txt`
(`evidence-manifest`, `budget-forecaster`, `reward-reconciler`,
`evidence-harness`, `schema-checker`) and matched exactly.

Two directories exist alongside the 23 named tools that are **deliberately
not** in `baselines.json`: `evidence-validator` (a real, runnable tool that
was simply outside the documented scope of this task) and `repo-root`
(not a tool at all -- just `README.md`/`LICENSE`/`.gitignore`, no script).
Running the checker against the full tree surfaces both as
`UNBASELINED_TOOL`, which is the intended behavior, not a bug: the
checker refuses to pretend a directory it doesn't know about is fine.

## A real bug I found while building this (and how it resolved)

While validating that the checker's reports are truly location-independent
(no absolute paths baked into any *tool's* own report, not just the
checker's own report), I copied the entire sibling-tools tree to
`/tmp/relocated_outputs` and reran the full baseline against the copy.
`bundle-index` showed up with `REPORT_HASH_DRIFT`: `file_count` dropped
from 10 to 9 and two `SUSPICIOUS_ARTIFACT` findings disappeared. That
looked exactly like the kind of environment-dependent bug this checker is
built to catch.

Root cause, after diffing the two reports and then diffing the two bundle
directories file-by-file: my own relocation script ran
`find /tmp/relocated_outputs -name "__pycache__" -exec rm -rf {} +` to
tidy up compiled bytecode -- but `bundle-index`'s own `bundle_bad` test
fixture *intentionally* contains a file at
`bundle_bad/__pycache__/main.cpython-310.pyc`, used as bait for the
`SUSPICIOUS_ARTIFACT` check. My cleanup command deleted that fixture file
along with real bytecode caches elsewhere in the tree. Re-running the
relocation copy without deleting anything reproduced the exact original
hash. **`bundle-index` is not location-dependent; my test harness was
briefly buggy.** I'm reporting this in detail because it is a fair
illustration of exactly the kind of false positive a regression checker
can produce, and why every drift result needs a human to look at the
`detail` block before concluding "the tool broke."

I also swept all 23 baselined tools for `PYTHONHASHSEED` sensitivity
(Python randomizes `str` hashing per-process by default, which can leak
into output ordering if a tool ever iterates a `set`/`dict` built from
one) and for `TZ` sensitivity on the two tools that take `--now`
(`staleness-monitor`, `loop-health`). Neither turned up any drift across
23 tools x 2+ seeds/timezones -- a genuinely clean result, reported as
such rather than manufactured.

## 3 limitations a reviewer should scrutinise

Two of the three limitations previously listed here (`expected_exit_code:
false` accepted as `0`, and a `report_mode: "file"` report trusted no
matter how the process died) are now **fixed**, with the before/after runs
recorded in `captured_output.txt`. What follows are the limitations that
are actually still true.

1. **`ABNORMAL_TERMINATION` is POSIX-only in practice.** The signal check
   is `returncode < 0`, which is how CPython's `subprocess` reports a
   signalled child on POSIX. On Windows there is no such convention: a
   process terminated by the OS surfaces as a large positive exit status
   (e.g. `0xC0000005` for an access violation), which this checker will
   compare against the baseline as an ordinary exit code and report as
   `EXIT_CODE_DRIFT`, not `ABNORMAL_TERMINATION`. The six
   signal-dependent tests in `test_regress_integrity.py` are explicitly
   `skipUnless(os.name == "posix")` rather than silently passing on
   Windows. Nothing here has been run on Windows.

2. **A tool that writes a complete-looking but wrong report and exits `0`
   is still indistinguishable from a correct one.** The new termination
   check catches processes that *died*; it says nothing about processes
   that finished normally and were simply wrong. The `0-byte` refusal in
   `--update-baselines` is a heuristic for the commonest case (died before
   writing anything) and nothing more -- a tool that writes one truncated
   line and exits `0` will still be baselined. `detail.report_bytes_length`
   remains the field a human has to eyeball for that.

3. **`make_fixtures.py --check` is self-referential.** It re-runs the
   *current* generator into a temp directory and diffs. That catches a
   hand-edited `fixtures/` tree, which is what it is for, but an error
   inside the generator itself reproduces identically in both runs and is
   therefore invisible to `--check`. The only real guard against that is
   the assertions in `test_regress_integrity.py::TestFixtureGenerator`,
   which check properties of the tree (seven tool directories, exactly two
   `unbaselineable` entries, `ghost_tool` has no directory, no absolute
   interpreter path, no boolean exit codes) rather than re-deriving it.

# coverage_audit.py -- baseline coverage auditor

`regress.py` answers "did an already-baselined tool drift?". It is
structurally unable to answer a prior, cheaper question: **is baseline
coverage of the repository even complete?** A directory with zero
baseline entry, or a baseline entry with zero directory, or a baselined
directory whose entrypoint script has been deleted, all currently get
folded into `regress.py`'s single `drift` bucket alongside real exit-code
and hash mismatches. `coverage_audit.py` is a separate CLI that keeps
those apart, checks **every** tool directory in the repository (not just
the 23 named in `baselines.json`), and reruns every baselined one from
scratch.

Stdlib only: `argparse`, `hashlib`, `json`, `os`, `re`, `subprocess`,
`sys`, `tempfile`. No third-party packages, no network access. Verified
on CPython 3.11.15 / Linux x86_64.

## Usage

```
python3 coverage_audit.py [--root DIR] [--baselines FILE] [-o FILE] [--timeout SECONDS]
```

Run from `regression-checker/` (the defaults assume this): `--root`
defaults to `..` (the repo root, so every sibling tool directory is
discovered) and `--baselines` defaults to `baselines.json` (this
directory's own committed file).

- `--root PATH` -- directory containing tool subdirectories (default `..`)
- `--baselines PATH` -- baseline JSON file (default `baselines.json`)
- `-o, --output PATH` -- write the report JSON here instead of stdout
- `--timeout SECONDS` -- per-tool subprocess timeout (default `120`)

## The six states

Every tool directory under `--root`, and every name in `baselines.json`,
ends up in **exactly one** of these states. They are checked in this
order, so a directory that fails an earlier check is never subsequently
misclassified by a later one:

| State | Meaning | Checked before executing anything? |
|---|---|---|
| `not_baselined` | directory exists, no entry in `baselines.json` | n/a -- no command to run |
| `orphaned_baseline` | entry exists in `baselines.json`, no directory under `--root` | yes -- `cwd=` would fail |
| `source_missing` | entry + directory both exist, but the script the command names (e.g. `forecast.py`) is not present in that directory | **yes** |
| `unrunnable` | the interpreter/binary could not be launched at all, or the run timed out | n/a -- this *is* the execution attempt |
| `stale` | it ran, but the actual exit code and/or the actual report's sha256 does not match the baseline (or the report file the baseline expects was never created) | no -- this is the post-execution comparison |
| `reproducing` | it ran, and both the exit code and the report hash matched the baseline exactly | no |

`source_missing` and `unrunnable` are **never** reported as `reproducing`
-- there is no path through `classify()` that lets either fall through to
the exit-code/hash comparison, because both `return` before any
comparison is attempted (`source_missing` returns before `run_command` is
even called; `unrunnable` is `run_command` itself reporting it could not
obtain a result).

## Exit codes

| Code | Meaning |
|---|---|
| `0` | every directory (baselined or not) is `reproducing` |
| `1` | ran to completion, but at least one directory is `not_baselined`, `stale`, `orphaned_baseline`, `source_missing`, or `unrunnable` |
| `2` | setup error -- `baselines.json` missing/unreadable/malformed, `--root` not a directory, or `--output` could not be written. Nothing was audited. |

This is deliberately stricter than "just check `not_baselined`/`stale`":
the brief requires those two to force nonzero, and `0` is reserved for
the state where the coverage story is fully green -- a directory that
lost its source file, or a baseline entry that lost its directory, is
exactly the kind of silent decay this tool exists to catch, so it also
forces nonzero rather than being waved through as "not technically
drift".

## The bool-coercion fix (not inherited)

In Python, `bool` is a subclass of `int`: `isinstance(True, int)` is
`True`, and `False == 0`. A naive `isinstance(expected_exit_code, int)`
check therefore accepts a baseline's `"expected_exit_code": false` and
then silently treats it as a match against any real exit code of `0`
(and `true` against `1`). `regress.py` in this same directory already
fixed this defect (see `REVIEWERS_GUIDE.md` §4.6, "CLOSED"); the fix is
`is_exit_code()`:

```python
def is_exit_code(value):
    return isinstance(value, int) and not isinstance(value, bool)
```

`coverage_audit.py` reimplements the identical check independently
(`coverage_audit.is_exit_code`) rather than importing `regress.py`, so it
does not inherit the bug by construction and does not depend on
`regress.py` staying fixed. `load_baselines()` calls it while parsing
every entry; a boolean `expected_exit_code` makes the **whole baselines
file** fail to load with `SetupError` (exit `2`) -- rejected outright, at
parse time, before a single tool is run, never silently coerced to `0`.
`test_coverage_audit.py::TestLoadBaselinesEntryValidation::test_expected_exit_code_bool_false_raises_not_coerced`
and `...bool_true_raises` pin this directly, and
`TestCLI::test_cli_exit_two_on_bool_expected_exit_code` pins it at the
subprocess/CLI level (exit `2`, message contains "boolean").

## The committed report

`baseline_coverage_report.json` in this directory is the **unedited**
output of:

```
cd regression-checker && python3 coverage_audit.py -o baseline_coverage_report.json
```

Its `counts` block and the length of its `results` array are independently
derivable by a reviewer: every integer in `counts` except
`discovered_directories`/`baseline_entries`/`total_records` is a count of
`results` entries with that `state`, and

```
counts.reproducing + counts.stale + counts.not_baselined
  + counts.orphaned_baseline + counts.source_missing + counts.unrunnable
  == counts.total_records == len(results)
```

holds exactly (`test_coverage_audit.py::TestBuildReportAllStates` pins
this identity on a synthetic tree with all six states present at once;
`TestRealRepository::test_totals_sum_to_45` pins it against the real
repo).

## A real bug hunt finding: `bundle-index`'s baseline does not reproduce

Running the audit (not reasoning about it) surfaced one baselined tool
that does not currently reproduce: **`bundle-index`**.

Its baseline entry runs:

```
python3 bundle_index.py bundle_bad -o {REPORT}
```

expecting exit code `1`. But `bundle-index/` only commits a `bundle_ok/`
fixture directory -- `bundle_bad/` **is not present** in the tree. The
actual run is:

```
$ cd bundle-index && python3 bundle_index.py bundle_bad -o /tmp/x.json
bundle_index: input error: bundle directory 'bundle_bad' does not exist
$ echo $?
2
```

Exit `2`, not the baselined `1`, and no report file is ever written.
`coverage_audit.py` reports this as `state: "stale"` with
`reasons: ["exit_code_mismatch", "report_not_created"]` -- it is not
hidden, tuned away, or silently reclassified as `reproducing`. This is
reported here exactly as observed:
`test_coverage_audit.py::TestRealRepository::test_bug_hunt_finding_bundle_index_is_stale`
pins it, and `test_reproducing_count_is_22` / `test_stale_count_is_1`
pin that every *other* baselined tool (all 22 of them) does reproduce --
this is a single, isolated, named divergence, not a systemic one.

(`bundle-index/README.md` itself documents a related but different
gotcha -- writing `-o` *inside* the directory being indexed changes the
next run's result -- which is not what is happening here; the fixture
directory this baseline names simply is not committed.)

## Determinism proof, including a relocation leg

Two runs from the same checkout, plus a third run from the *repository
copied to a differently-named absolute path*, all hash identically. Two
same-directory runs alone cannot detect a tool that leaks its own
absolute path into the report (the leak would be identical both times);
the relocation leg is what actually tests for that.

```
$ cd regression-checker && python3 coverage_audit.py -o /tmp/run1.json
$ cd regression-checker && python3 coverage_audit.py -o /tmp/run2.json
$ cp -r <repo> /tmp/reloc_xyz_29718   # differently-named absolute path
$ cd /tmp/reloc_xyz_29718/regression-checker && python3 coverage_audit.py -o /tmp/run3_reloc.json
```

| Run | sha256 of report |
|---|---|
| run1 (original path) | `40dc7f3f3c304cfb18c42b94a1bd291c7bf67fd16b9dd4eab11ed8972cc45de0` |
| run2 (original path, second run) | `40dc7f3f3c304cfb18c42b94a1bd291c7bf67fd16b9dd4eab11ed8972cc45de0` |
| run3 (relocated to a differently-named path) | `40dc7f3f3c304cfb18c42b94a1bd291c7bf67fd16b9dd4eab11ed8972cc45de0` |

All three identical. No absolute path, hostname, or timestamp reaches the
report: `--root` and `--baselines` themselves are never written into it,
the only filesystem-derived strings that appear are relative tool-dir
names and single-component script filenames (e.g. `"forecast.py"`), and
`canonical_json()` never reads a clock.

## Limitations (real failure modes, not hedges)

1. **A single non-Python interpreter breaks source-missing detection
   silently degrading to `unrunnable`.** `find_script_token()` special-
   cases `python`/`python3`/`python3.NN` as `command[0]` and otherwise
   falls back to scanning for the first token ending in `.py`. A baseline
   command like `["bash", "run.sh"]` (no `.py` token anywhere) makes
   `find_script_token()` return `None`, so `source_missing` is *never*
   checked for that entry -- a deleted `run.sh` is only discovered when
   `subprocess.run` raises `FileNotFoundError` inside `run_command`,
   which is correctly reported as `unrunnable` rather than
   `reproducing`, but the more specific and more informative
   `source_missing` state is lost. Every real entry in this repository's
   `baselines.json` is `python3 <script>.py ...`, so this has not fired
   here -- but it is a concrete, named gap, not a hypothetical one.
   `TestFindScriptToken::test_no_py_token_returns_none` pins the exact
   input that triggers it.

2. **`status: "unbaselineable"` (which `regress.py` supports) is treated
   as a malformed baselines file, not a skip.** `regress.py` has a whole
   code path for a tool that is deliberately never rerun (e.g. it needs
   network access or wall-clock nondeterminism it cannot be baselined
   against) via `"status": "unbaselineable"` plus a `"reason"` string.
   `coverage_audit.py`'s `load_baselines()` requires `status ==
   "baselined"` for every entry and raises `SetupError` (exit `2`,
   refusing to audit *anything*) the moment it meets any other value,
   including `"unbaselineable"`. The real `baselines.json` in this repo
   has zero such entries today, so this has never fired against real
   data -- but if one is ever added without updating this loader, the
   entire audit stops running instead of degrading gracefully.
   `TestLoadBaselinesEntryValidation::test_status_unbaselineable_raises`
   pins the exact input.

3. **A tool that writes a complete, correctly-hashed, but observably
   *wrong* report and exits with the expected code is indistinguishable
   from a genuinely correct one.** `reproducing` means "exit code and
   report bytes match the committed baseline", nothing more. If the
   original baseline itself was recorded from a buggy run (a bad
   `expected_report_sha256` blessed once, at `--update-baselines` time,
   in `regress.py`, and never revisited), `coverage_audit.py` will keep
   calling that tool `reproducing` forever -- reproducibility and
   correctness are different properties, and this tool only measures the
   first.

4. **`is_exit_code`/hash validation happens per-entry, but a malformed
   entry aborts the *entire* run, not just that one tool.** `SetupError`
   during `load_baselines()` (a boolean `expected_exit_code`, a bad
   `report_mode`, etc., on *any single entry*) means `build_report()` never
   even calls `discover_tool_dirs()` -- one bad entry among 23 valid ones
   produces exit `2` with zero per-directory results, not "22 audited, 1
   flagged". This is intentional (see "Booleans are not exit codes" in
   `regress.py`'s own docstring for the same design choice) but it does
   mean a single typo in `baselines.json` can silence the coverage report
   for every other tool in the same run.
   `TestBuildReportSetupErrors::test_malformed_baselines_raises_before_touching_root`
   pins this.
