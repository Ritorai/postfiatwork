# adversarial-suite

A stdlib-only Python 3 regression suite for the three tools in this
repository whose READMEs, before `limitations-probe/` ran them against
hostile input, disclosed **no limitations at all**: `evidence-manifest`,
`reward-reconciler`, `schema-checker`. `limitations-probe/` already did the
documentation pass and the READMEs already carry a "limitations a reviewer
should scrutinise" section sourced from it. This directory does not repeat
that work. It turns those findings -- plus a few more turned up independently
while building this suite -- into a **committed, runnable, `unittest`-based
regression suite**: real subprocess invocations, real exit codes, real
stdout/stderr, asserted byte-for-byte or field-for-field, with fixtures that
round-trip from a generator and run evidence from two locations on disk.

## Reproduce command

```
cd adversarial-suite
python3 make_fixtures.py            # generate fixtures/ (idempotent)
python3 -m unittest test_adversarial -v
```

That is the entire dependency chain. No third-party packages, no network,
Python 3 standard library only (`argparse` is not even used here --
`base64`, `filecmp`, `hashlib`, `json`, `os`, `shutil`, `subprocess`, `sys`,
`tempfile`, `unittest`).

**Observed, from an actual run in this checkout:**

```
Ran 122 tests in 8.9s

OK
```

122 is the number of `def test_` methods in `test_adversarial.py` --
`grep -c "def test_" test_adversarial.py` returns the same number. It is
**not** hardcoded as an assertion inside the suite, and nothing in the suite
fails if a future edit adds or removes a test. The lesson from the
"hardcoded 45 directories" incident cited in the task brief applies here:
this directory tests three tools by name, not the repository's shape.

**What is now checked is the sentence you just read, not the suite.**
`readmecounts.py` reads the numbers out of *this file* and compares each one
against the tree; see "Enforcing this README's counted claims" below. Adding
a test still does not fail the suite. It fails `readmecounts.py` until the
number above is updated -- which is the correct place for that failure,
because the number is a claim this document makes, not an invariant the
suite holds.

## Layout

| File | Purpose |
|---|---|
| `make_fixtures.py` | Generator. Regenerates `fixtures/` from base64 bytes embedded in this one file. `--verify` mode diffs a fresh regeneration against the committed `fixtures/` tree. |
| `fixtures/` | 120 generated fixture files + 3 empty directories, one subtree per tool. Committed as generator output, not hand-edited. |
| `test_adversarial.py` | 122 `unittest` tests across `EvidenceManifestTests`, `RewardReconcilerTests`, `SchemaCheckerTests`, `CrossToolFailureClassTests`, `OutputFileTests`, `MetaSelfConsistencyTests`. |
| `expected_results.json` | One record per adversarial case actually exercised: tool, argv (already relative, see below), exit code, and a sha256 of the normalized (exit code + stdout + stderr) payload. Regenerated by `test_adversarial.py`'s `_write_results_snapshot()` (see "Regenerating" below). |
| `captured_output.txt` | Transcript, in `transcript-drift/FORMAT.md` grammar, of three runs: two in the original checkout, one in a differently-named relocated copy. |
| `readmecounts.py` | Checks every counted claim in this README against the tree. Standard library only. Exit `0` all match, `1` a claim is stale or missing, `2` setup error. |
| `test_readmecounts.py` | 37 `unittest` tests for `readmecounts.py`, including the controls that neither side of the comparison is hardcoded, that an uncovered occurrence fails, and that `--with-digest` leaves an existing `fixtures/` untouched. |
| `stale_demo.py` | One-line-invocable demo: copies the checkable files to a throwaway path, makes one number stale, and shows the checker catching it. |
| `capture_counts.sh` | Regenerates `counts_captured_output.txt`. Deliberately **not** named `capture.sh` -- see the section below. |
| `counts_captured_output.txt` | Transcript of real `readmecounts.py` runs: clean tree, digest check, stale-claim demo, CLI contract, determinism. |

## What each adversarial fixture attacks

Grouped by axis, not by tool -- most axes are exercised against more than
one tool because that is what surfaced the cross-tool finding below.

- **Malformed / truncated / empty JSON** -- `empty_file.json`,
  `truncated.json`, `empty_file_expected.json`, `payload_empty_file.json`.
- **Wrong shape** -- object where an array is required
  (`wrong_shape_object.json`), `null` (`wrong_shape_null.json`,
  `wrong_shape_payouts.json`), a bare string, an array of non-objects,
  an array where schema-checker's root declares `object`
  (`payload_wrong_shape_array.json`).
- **NaN / Infinity / -Infinity** -- `nan_value.json`, `infinity_value.json`,
  `neg_infinity_value.json` (evidence-manifest, build succeeds and the
  literal token survives); `nan_amount_expected.json` (reward-reconciler,
  rejected -- see below); `payload_nan_as_number.json`,
  `payload_infinity_as_number.json` (schema-checker, silently conforms --
  new finding, see below). Python's `json` module accepts these by default
  and emits non-RFC-8259 output on `dumps`; this axis checks whether each of
  the three tools inherits that.
- **Duplicate object keys** -- `dup_keys_in_record.json` (evidence-manifest),
  `dup_task_id_expected.json` (a *field value* duplicate, reward-reconciler,
  rejected as invalid input -- different from a JSON-syntax duplicate key),
  `schema_dup_keys.json` / `payload_dup_keys.json` (schema-checker). All
  three exercise CPython's own last-value-wins behaviour for duplicate JSON
  object keys, which none of the three tools overrides with an
  `object_pairs_hook`.
- **Very deep nesting** -- `deep_nesting.json` / `deep_nesting_expected.json`
  / `payload_deep_nesting.json`, 3000 levels, one per tool. See the
  cross-tool finding below.
- **Huge integers** -- `huge_int.json` (500-digit integer, evidence-manifest,
  robust), `huge_valid_number_expected.json` (26-digit decimal amount,
  reward-reconciler, robust, contrasted with the exponent-notation crash).
- **Unicode**: astral-plane (`\U0001F600`), RTL override (`‮`), NFC vs
  NFD of the same rendered glyph, embedded NUL -- `unicode_astral_rtl_nul.json`,
  `unicode_nfc.json` / `unicode_nfd.json`, `embedded_null_in_id.json`
  (evidence-manifest); `payload_unicode_astral.json` (schema-checker,
  `max_length` counting).
- **CRLF vs LF, BOM, missing trailing newline** -- `crlf_in_string.json`
  (CRLF inside a JSON string value, collapsed like any whitespace),
  `crlf_file_level.json` (CRLF between JSON tokens, cosmetic, parses
  identically to LF), `bom.json` / `schema_bom.json` / `payload_bom.json`
  (UTF-8 BOM prefix, rejected -- `json.load(encoding="utf-8")` does not
  strip it), `no_trailing_newline.json` / `payload_no_trailing_newline.json`
  (robust).
- **Empty input files, directories where files are expected** --
  `dir_as_input/`, `dir_as_expected/`, `dir_as_payload/` (three empty
  directories, recreated explicitly by `make_fixtures.py` since `os.walk`
  drops empty directories and a naive tree copy would silently lose them).
- **Numbers as strings, booleans where ints are expected** --
  `bool_amount_expected.json` (`amount: true`, rejected -- `isinstance(x,
  bool)` checked explicitly, this bug class is closed here),
  `payload_bool_as_int.json` / `payload_float_integral_as_int.json` /
  `payload_float_extreme_as_int.json` (schema-checker's `SC-4`, all three
  correctly rejected -- negative result), `amount_as_int_expected.json`
  (a JSON integer amount, accepted -- only floats are rejected).
- **Report determinism: run twice, diff the bytes** -- every `*_expected`
  case is run twice within its own test (`test_*_byte_identical_across_two_runs`)
  and `OutputFileTests` repeats the same check through each tool's `-o` file
  path specifically, since that is the path each tool's own README uses for
  its determinism claim.

## Unreadable paths / permissions: tried, not usable here

The brief asks to try unreadable paths. `os.geteuid() == 0` in every
environment this suite has been run in (the sandboxed build container runs
as root), so `chmod 0` on a fixture file does not actually block a read --
confirmed empirically before writing any test around it (`os.chmod(path, 0)`
followed by opening the file as root still succeeds). Encoding a permission
test that silently passes for the wrong reason (root bypass, not
`PermissionError` handling) would be worse than not having it, so this axis
is represented instead by the **directory-as-file-argument** fixtures, which
raise a real `OSError` subclass (`IsADirectoryError`) regardless of the
invoking user's privileges, and turned out to reproduce a more interesting
failure (see below) than a plain permission-denied would have.

## Reproduced failure mode per tool

### evidence-manifest -- bare `NaN`/`Infinity` survive into the manifest (exit 0)

```
$ python3 manifest.py build ../adversarial-suite/fixtures/evidence-manifest/nan_value.json
{"algorithm":"sha256","batch_root":"...","entries":[{"canonical":{"score":NaN,"submission_id":"S1"},...}],...}
exit=0
```

`build` succeeds and the literal token `NaN` appears in the emitted JSON.
That is not valid RFC 8259 JSON: a strict parser (`json.loads(out,
parse_constant=<raising callback>)`, or Node/V8's `JSON.parse`) rejects it;
Python's own default parser and `jq` accept it. Pinned in
`test_bare_nan_survives_into_manifest_exit0` /
`test_bare_infinity_survives_into_manifest_exit0` /
`test_bare_negative_infinity_survives_exit0`, plus the reciprocal
`test_default_json_parser_accepts_the_manifest_anyway` so neither half of
the claim can go stale alone. This restates `limitations-probe`'s EM-3 as a
pinned regression rather than re-discovering it.

### reward-reconciler -- a split payout to the wrong wallet never names that wallet (exit 1)

```
$ python3 reconcile.py split_wrong_wallet_expected.json split_wrong_wallet_payouts.json
{"findings":[{"issue":"DUPLICATE_PAYOUT","payout_amount":"3.500000","task_id":"T1","wallet":"rHONEST",...}],"status":"mismatched",...}
exit=1
```

Expected: `3.5` to `rHONEST`. Actually paid: two payouts of `1.75` each, both
to `rATTACKER`. The report contains exactly one finding --
`DUPLICATE_PAYOUT`, naming the *expected* wallet `rHONEST` -- and the string
`rATTACKER` does not appear anywhere in the JSON report. `WALLET_MISMATCH`
never fires because the wallet-comparison code path only runs when there is
exactly one payout for a task; grouped (duplicate) payouts skip it entirely.
Pinned in `test_rr4_split_payout_to_wrong_wallet_never_names_that_wallet`,
directly asserting `"rATTACKER" not in json.dumps(doc)`. Contrasted with
`test_wallet_mismatch_detected_for_a_single_payout`, which confirms the
*same* comparison works correctly for a single (non-duplicate) payout --
isolating the defect to the split-payout branch specifically. Restates
`limitations-probe`'s RR-4, the more serious of its two `reward-reconciler`
findings.

### schema-checker -- `pattern` is matched with `re.search`, not a full match (exit 0)

```
$ python3 schema_check.py schema_pattern_unanchored.json payload_pattern_search.json
{"exit_code":0,"ok":true,"status":"conform","violation_count":0,"violations":[]}
exit=0
```

Schema: `{"type": "string", "pattern": "[0-9]{4}"}` (unanchored). Payload:
`"id": "XX1234XX"`. `_check_string()` calls `re.search(node["pattern"],
value)`, which matches the substring `1234` anywhere in the string and
therefore reports conformance. Pinned in
`test_sc1_unanchored_pattern_accepts_a_match_anywhere_in_string`, contrasted
with `test_sc1_contrast_anchored_pattern_correctly_rejects` (the identical
value against the same pattern anchored with `^...$` is correctly rejected)
to isolate the defect to unanchored schema authoring rather than to
`pattern` or `re.search` in general. Restates `limitations-probe`'s SC-1.

`schema-checker`'s other headline finding from `limitations-probe`, **SC-3**
(a schema-supplied `^(a+)+$` pattern hangs the checker indefinitely on
pathological input -- catastrophic regex backtracking, no match-time bound),
is also pinned here:
`test_sc3_redos_pattern_hangs_on_pathological_input` runs the tool with a
5-second subprocess timeout against 33 non-matching characters and asserts
`subprocess.TimeoutExpired` fires -- i.e. it asserts the tool does **not**
finish, which is the failure mode. `test_sc3_contrast_same_pattern_short_non_match_is_fast`
confirms the same pattern against a shorter non-matching string returns well
within budget, so the timeout in the first test measures the tool
pathologically hanging, not a slow environment.

## New findings (not in `limitations-probe/`, found while building this suite)

`limitations-probe/probe.py` runs 12 fixed, hand-picked probes. Running each
tool against the broader adversarial axes required by this task's brief
turned up three more, unrelated to those 12:

1. **These tools crashed with an unhandled traceback and exited 1 -- not
   their own documented exit 2 for "invalid input" -- on a directory passed
   where a file argument was expected**, and on JSON nested ~3000 levels
   deep (`RecursionError`). **`reward-reconciler` was repaired in the
   exit-code alignment delivery and now exits 2 for both**, so the cases
   here pin that repair instead of the defect; `evidence-manifest` still
   crashes and the tests still say so. Neither
   `evidence-manifest/manifest.py`'s `load_records()` nor, at the time this
   was written, `reward-reconciler/reconcile.py`'s `_load_records()`
   caught anything but `FileNotFoundError` around `open()` and
   `json.JSONDecodeError` around `json.load()`; `IsADirectoryError` and
   `RecursionError` are both neither, so they propagate to Python's default
   top-level handler, which prints a traceback and exits 1. Exit 1 is
   "verification drift" (evidence-manifest) or "mismatched" (reward-
   reconciler) in each tool's own documented contract, so a caller that
   branches only on exit code will file an unreadable/malformed input as a
   *content* finding rather than a processing failure. Pinned per-tool
   (`test_directory_as_records_path_crashes_uncaught_exit1`,
   `test_deep_nesting_crashes_uncaught_recursionerror_exit1`, and their
   `reward-reconciler` equivalents) and cross-tool
   (`CrossToolFailureClassTests`, run as `subTest`s so one command shows
   the pattern holding across both tools at once).

   **`schema-checker` is the exception, not another instance.**
   `schema_check.py`'s `load_json_file()` explicitly wraps the read in
   `except OSError`, so the *same* directory-as-argument input is a clean
   `IO_ERROR` at exit 2, not a crash --
   `test_directory_as_payload_handled_gracefully_exit2` and
   `test_schema_checker_is_the_exception_to_the_pattern_for_directories`
   pin the contrast explicitly. `RecursionError` from deep nesting still
   escapes schema-checker the same way it escapes the other two, though
   (`test_deep_nesting_payload_crashes_uncaught_recursionerror_exit1`) --
   `OSError`/`UnicodeDecodeError`/`JSONDecodeError` do not cover it, so the
   more defensive tool is only partially immune to this failure class.

2. **`schema-checker` silently accepts JSON `NaN`/`Infinity`/`-Infinity` for
   a field typed `number`.** `json_type()` maps any Python `float` to the
   schema type name `"number"` without checking `math.isnan`/`isinf`, so a
   field declared `{"type": "number"}` with no `minimum`/`maximum` conforms
   for all three non-finite values --
   `test_new_nan_silently_conforms_as_number_type` and its two siblings.
   This is a genuine gap, not a restatement of `SC-4`: `SC-4` is about
   `type: integer` correctly rejecting `bool` and integral/extreme floats
   (still true, still pinned here as a negative result), which is a
   different code path (`TYPE_MISMATCH` fires because a `float` is not an
   `int`). The gap here is specific to a field actually typed `number`,
   where the type check alone cannot distinguish `NaN` from any other
   float, and no bound comparison exists to catch it either.

## Negative results: axes tried, tool proved robust

Recorded because the brief asks for them explicitly, not because a positive
finding was expected and missing:

- **Huge integers** (500 digits, evidence-manifest) and **huge decimal
  amounts without scientific notation** (26 digits, reward-reconciler) round
  -trip exactly; Python's arbitrary-precision `int` and `decimal.Decimal`
  do not overflow. Contrasted directly with `RR-2`
  (`"1E+999999999"`, exponent notation), which used to crash: the defect was
  in exponent handling specifically, not magnitude. `RR-2` has since been
  repaired and that input now exits 2 with an `INVALID_INPUT` report; the
  magnitude/exponent distinction it illustrated still stands.
- **`bool` amounts are rejected** by `reward-reconciler`
  (`isinstance(raw, bool)` is checked explicitly before the general
  `isinstance(raw, (str, int))` gate) -- the exact bug class documented as
  *open* for `regression-checker/regress.py` in `REVIEWERS_GUIDE.md` §4.6 is
  closed here.
- **`schema-checker`'s `type: integer` correctly rejects `true`, `5.0`, and
  `1e400`** (`SC-4`, restated with three separate pinned tests, one per
  value, rather than one combined test, so a future regression in exactly
  one of the three does not hide behind the other two still passing).
- **CRLF at the file/token level, a missing trailing newline, and duplicate
  JSON object keys** are all handled without incident by all three tools
  (last-value-wins for duplicates, whitespace is whitespace to the parser
  either way).
- **Astral-plane characters, an RTL override control character, and an
  embedded NUL byte** all survive `evidence-manifest`'s canonicalization and
  round-trip correctly as `ensure_ascii=True` `\uXXXX` escapes (including
  the UTF-16 surrogate pair for the astral character).
- **A directory passed as the payload path is handled cleanly by
  `schema-checker`** (see "New findings" above) -- the one tool of the three
  that is *not* vulnerable to this particular crash class.

## What is normalized, and why

Every test invokes its target tool as a subprocess with `cwd` set to that
tool's own directory (e.g. `.../evidence-manifest`), and every fixture/output
path on `argv` is computed with `os.path.relpath()` *relative to that
directory* at test-run time -- never as an absolute string, never hardcoded.
That alone makes the vast majority of tool output relocation-safe for free:
none of the three tools' own error messages (`INVALID_INPUT: file not
found: <path>`, `IO_ERROR ... cannot read ... file "<path>"`, etc.) resolve
the path to absolute before printing it -- they echo back exactly the
string that was passed on argv, confirmed empirically (see
`rel_to_tool()`'s docstring in `test_adversarial.py`).

The one place an absolute path leaks in regardless is a Python traceback for
an *uncaught* exception (the crash cases described above): CPython resolves
the invoked script's own path to absolute for the `File "..."` line in a
traceback even when it was invoked with a relative path
(`python3 manifest.py ...` from the right `cwd` still prints
`File "/abs/path/to/evidence-manifest/manifest.py", line N`). That absolute
prefix is exactly, and only, the repository root -- CPython's own standard
library paths (`/usr/lib/python3.11/json/decoder.py` etc.) are identical
across the original and relocated runs because they are not part of what
gets relocated.

`normalize()` in `test_adversarial.py` therefore does exactly one
substitution: the absolute path of the repository root, computed at
test-run time as `os.path.dirname(HERE)`, replaced with the literal token
`<REPO_ROOT>`. It is applied to every captured stdout/stderr string before
that string is hashed into `expected_results.json`'s `output_sha256`
fields, and before the whole `RESULTS` dict is hashed into the single
digest that `captured_output.txt` compares across the three runs below. No
other substitution is performed -- there is nothing else that differs
between an original-path run and a relocated-path run, because every other
path in this suite is already relative to something that moves together
with the checkout.

## Relocation: two runs in the original checkout, one after moving the tree

```
cd /tmp/build_4/repo/adversarial-suite
python3 make_fixtures.py
python3 -m unittest test_adversarial -v
python3 -m unittest test_adversarial -v
python3 test_adversarial.py --digest      # prints RESULTS_DIGEST to stderr

cp -r /tmp/build_4/repo /tmp/build_4/relocated_xyz
cd /tmp/build_4/relocated_xyz/adversarial-suite
python3 test_adversarial.py --digest
```

`--digest` runs the full suite in-process (same test code, same assertions
as `python3 -m unittest`) and additionally prints
`RESULTS_DIGEST sha256=<hex> cases=<n>` to stderr: a single sha256 over the
canonical (sorted-key) JSON encoding of every case's normalized `argv` /
`exit_code` / stdout / stderr recorded during that run. All three digests
below are **byte-identical strings**, observed from three separate process
invocations, two before the tree moved and one after:

| Run | Location | Result | `RESULTS_DIGEST` (sha256) |
|---|---|---|---|
| 1 | `/tmp/build_4/repo` (original) | `Ran 122 tests in 9.488s` / `OK`, exit 0 | `6246d36b30c93763f0463633f5352d611d58ef7763bad44803f1174f6aa2cbdf` |
| 2 | `/tmp/build_4/repo` (original, rerun) | `Ran 122 tests in 9.416s` / `OK`, exit 0 | `6246d36b30c93763f0463633f5352d611d58ef7763bad44803f1174f6aa2cbdf` |
| 3 | `/tmp/build_4/relocated_xyz` (relocated) | `Ran 122 tests in 10.840s` / `OK`, exit 0 | `6246d36b30c93763f0463633f5352d611d58ef7763bad44803f1174f6aa2cbdf` |

See `captured_output.txt` for the exact commands and their full output,
including the three `RESULTS_DIGEST` lines with the actual hex digests. The
three digests match each other exactly; that equality is the relocation
proof this task's verification bar asks for.

## Enforcing this README's counted claims

This file states five distinct integers and one hash about this
directory, plus one claim (`grep_test_count`) that states no numeral of
its own -- it asserts that a `grep` returns the same number as one of the
others. Until now every one of them was prose, and prose does not fail.

`readmecounts.py` closes that. It reads each number **out of this file**
and compares it against the tree.

```
python3 readmecounts.py
python3 readmecounts.py --with-digest
python3 readmecounts.py -o counts_report.json --quiet
python3 stale_demo.py --claim case_count
python3 -m unittest test_readmecounts
```

Exit `0` when every claim is found and matches, `1` when one is stale,
missing, or stated somewhere the checker cannot see, `2` on a setup
error.

| Claim | Stated where | Measured from |
|---|---|---|
| `test_count` | the observed-run block, the Layout table, the "N is the number of `def test_` methods" sentence, the relocation table's three `Ran N tests` cells, and limitation 4's "smaller than the test count (N)" | `def test_*` methods in `test_adversarial.py`, counted from the syntax tree |
| `grep_test_count` | this file's claim that `grep -c "def test_" test_adversarial.py` "returns the same number" | actually doing that count |
| `fixture_file_count` | the Layout table, the `VERIFY OK` line, and limitation 3's "N fixtures against three tools" | `len(FIXTURES_B64)` in `make_fixtures.py` |
| `empty_dir_count` | the Layout table and the `VERIFY OK` line | `len(EMPTY_DIRS)` in `make_fixtures.py` |
| `case_count` | limitation 4's "case count (N," and the relocation section's "`cases=N` in all" | `len(expected_results.json["cases"])` |
| `own_test_count` | the Layout table row for `test_readmecounts.py` | `def test_*` methods in `test_readmecounts.py` |
| `results_digest` | the three-row relocation table | running `test_adversarial.py --digest` for real (`--with-digest`, ~10s) |

Four properties are worth stating plainly, because a checker like this
can be worthless in four different ways:

**1. No expected value lives in `readmecounts.py`.** It contains locator
patterns and measurement functions and not one of the numbers it checks
-- not in the code and not in the docstring either.
`test_no_claimed_value_appears_in_the_checker_source` searches the entire
file for each measured value as a standalone number and requires zero
hits. It checks *every* claim: an earlier version skipped values shorter
than three characters, which silently exempted a third of them.

**2. Neither side of the comparison is frozen.** One test edits a number
in a copied README and requires the reported expectation to move with it;
another appends a real test method to a copied `test_adversarial.py` and
requires the measured value to move with it. The edit itself is derived
from `LOCATORS` (`readmecounts.bump_claim`) rather than written as a
literal, so a legitimate future edit that changes a number does not turn
this suite red -- the failure mode a test containing a literal copy of
the observed-run line would have.

(That sentence used to quote the literal line, and the checker caught it:
the quote counted as an occurrence of `test_count` in a place no locator
covered, and the run failed. Rewording it was the right fix. The precise
version of the anecdote, since the loose one flatters the tool: a
*backticked* quotation of that line is absorbed by one of `test_count`'s
own locators and read as a claim rather than a stray, so it is the
unbackticked form the sweep catches. The same thing happened in
`readmecounts.py`'s own docstring, where an illustrative number had to be
replaced with `N` -- caught by the hardcoded-values control, on a real
run.)

**3. A number stated twice must agree with itself, and every occurrence
must be visible to the checker.** Several of these numbers appear in more
than one place. Each occurrence a locator matches is read, and if they
disagree the state is `internal_disagreement` rather than a plain
mismatch. That alone is not enough, and the first version of this section
overclaimed on exactly this point: locators are hand-written, so a number
can sit in a sentence none of them match, go stale there, and be reported
clean. Two such sentences existed in this file when the tool was written
-- limitation 3's fixture count and limitation 4's test count. So after
matching, every NUMERIC claim also sweeps the whole README for its own
value and reports anything the locators did not cover as
`unlocated_occurrence`, which fails the run.

A second review then found a one-character bypass in the sweep itself.
The pattern was `(?<![\w.])N(?![\w.])`, which refuses to match when the
next character is a full stop -- so a stale number at the end of an
ordinary English sentence was invisible, and a README stating two
different test counts could still exit `0`. The same pattern was shared
with the no-hardcoded-values control in **1**, so that had the identical
hole. It now matches a sentence-final number and still rejects `N.5` and
`Nth`; both directions are pinned by tests.

Three limits remain, stated rather than buried. The sweep requires the
value to sit near the claim's own vocabulary (`CONTEXTS`), because
sweeping for a small number with no context flags a Python version and a
table row number instead -- so a stale occurrence with no nearby keyword
is not swept up. `results_digest` is not swept at all: a 64-character
hash will not appear by coincidence, and sweeping it would flag its own
three table rows, so a stale copy of the digest in prose would not be
caught. And the sweep looks for the *correct* value, so a sentence
inventing a number that was never right anywhere is not its job.

**4. A missing claim is a failure, not a pass.** Deleting the sentence a
claim lives in yields `claim_text_not_found` and exit `1`. Silence must
not read as agreement.

`readmecounts.py` checks its own suite size too (`own_test_count`), so
the row in the Layout table above is held to exactly the rule it
describes.

`--with-digest` has to generate `fixtures/` to run the suite. An existing
`fixtures/` is **moved aside and moved back**; one that the run created is
removed. Either way the tree is left as it was found, and
`counts_captured_output.txt` records both cases, the second with a canary
file. The first version got this wrong in a way worth recording: it
guarded its own `rmtree` and then shelled out to `make_fixtures.py`,
whose `generate()` removes the destination itself, so a pre-existing
`fixtures/` and everything in it was destroyed. Guarding only the lines
you wrote is not the same as not destroying anything.

`--with-digest` also cross-checks the `cases=N` the suite prints against
`expected_results.json`, and refuses a run that recorded zero cases.
Without that, a generator that failed left an empty result set whose
digest -- the hash of `{}` -- was reported as a perfectly good match: a
vacuous pass in the middle of a tool built to catch vacuous passes.

### Why the transcript is `counts_captured_output.txt`, not `captured_output.txt`

The committed `captured_output.txt` in this directory records three timed
runs of the full adversarial suite on a machine whose paths
(`/tmp/build_4/...`) no longer exist. It is the relocation proof for the
suite itself and it cannot be reproduced here; overwriting it would
destroy real evidence and replace it with different real evidence. That
editorial reason is the main one, and it stands on its own.

There is a mechanical reason too, and it is worth stating precisely
rather than dramatically. `regen-preflight` discovers transcript
regenerators by the exact name `capture.sh`, runs each in a throwaway
copy, and byte-compares the sibling `captured_output.txt` before and
after. A `capture.sh` here that wrote some *other* file would therefore
be re-run on every preflight and reported `match` -- not because it
reproduced anything, but because it never touched the file being
compared. That is a vacuous pass, the same shape as a test that asserts
nothing, and this repository has one of those already. Naming the script
`capture_counts.sh` keeps it out of a check it cannot honestly satisfy.

(Checked, not assumed: `regen-preflight/regenpre.py` and
`inventory_counts.py` key on the literal `"capture.sh"`;
`transcript-drift/driftcheck.py` and
`transcript-schema/validate_transcript.py` key on the literal
`"captured_output.txt"`. Renaming this script to `capture.sh` and running
`regenpre.py --phase transcripts --only adversarial-suite` really does
come back `match` while regenerating nothing.)

**The cost of that choice, stated as a cost rather than as a feature.**
`counts_captured_output.txt` is scanned by no repo-wide tool, and it
repeats every number in this section several times over. That makes it a
further home for numbers this section exists to stop duplicating, and
`readmecounts.py` reads only `README.md`, so those copies are not checked
against anything. Regenerating the transcript after a README change is
what keeps them honest, and nothing enforces that. It validates clean
when pointed at by hand:
`python3 ../transcript-schema/validate_transcript.py counts_captured_output.txt`.

## Regenerating `expected_results.json`

```
python3 -c "
import test_adversarial as t, unittest
r = unittest.TextTestRunner(verbosity=0).run(
    unittest.TestLoader().loadTestsFromModule(t))
t._write_results_snapshot()
"
```

Not run automatically by the test suite itself (a test suite that rewrites
its own expected-output file on every invocation cannot ever fail), but
deterministic and idempotent: running it twice in a row produces a
byte-identical `expected_results.json`, because every value that goes into
it is either already normalized or path-independent by construction.

## 3+ limitations of this suite itself

Named against real input shapes that defeat it, per the task brief's
explicit instruction not to hand-wave with "may produce false positives":

1. **The ReDoS test (`SC-3`) is a timing assertion, and timing assertions
   are the least portable kind.** `test_sc3_redos_pattern_hangs_on_pathological_input`
   asserts the tool is *still running* after a 5-second subprocess timeout.
   On a sufficiently fast machine (or a future Python whose `re` module
   gains linear-time matching for this pattern class -- under discussion
   upstream, not shipped as of 3.11), 33 characters against `^(a+)+$` could
   finish inside 5 seconds and this test would report a false NEGATIVE
   (looks like the bug is fixed when it is only faster). Conversely, a
   sufficiently loaded/throttled CI runner could make the *fast* contrast
   test (`test_sc3_contrast_same_pattern_short_non_match_is_fast`, budgeted
   at the same 5 seconds for a 10-character non-match that runs in ~30ms
   locally) flaky under extreme contention. Neither failure mode was
   observed in any run performed for this deliverable, but both are
   possible in principle and neither can be fixed by better assertions --
   only by widening the exponent (more `a`s) to push the true runtime
   further from any plausible timeout, which this suite does not do because
   it would make the *whole suite* slower on every run, on every machine,
   forever, to protect against a scenario that has not occurred.

2. **The directory-argument crash tests are unverifiable as a permission
   proxy on this specific runtime (root).** As documented above under
   "Unreadable paths / permissions", this suite could not exercise a real
   `PermissionError` because the container runs as `root`, which bypasses
   file-mode bits entirely. The directory-argument fixture reproduces a
   *different* uncaught `OSError` subclass and is a faithful test of "any
   OSError besides FileNotFoundError crashes these two tools", but it does
   NOT prove that a permission-denied file produces the identical crash --
   only that the code path (`except FileNotFoundError` and nothing broader)
   makes it structurally likely. A reviewer running this suite as a non-root
   user could extend it with a real `chmod 000` case; this suite does not,
   because doing so here would have produced a fixture that silently tests
   nothing (a `PermissionError` that root's `open()` never raises) while
   still reporting green.

3. **Fixture coverage is deep on the axes the task brief names, not
   exhaustive over the schema DSL or the reconciliation join logic.** 120
   fixtures against three tools finds real bugs (four independently
   reproduced, plus the twelve already in `limitations-probe/`) but a
   combinatorial adversary -- e.g. a schema mixing `unique_items` with
   nested `object` items where two items are unequal as JSON but equal
   under this suite's `max_length`/Unicode quirks simultaneously, or a
   reconciliation batch exercising `DUPLICATE_PAYOUT` and `WALLET_MISMATCH`
   in the same batch across hundreds of tasks to check for an aggregation
   bug in `issue_counts` -- is not attempted. The three "reproduced failure
   mode" bugs plus the two new findings above were each found by trying one
   adversarial idea at a time against real output, per the brief's
   instruction to run rather than read; a combinatorial fuzz harness over
   the schema DSL specifically would be a reasonable next suite, not this
   one.

4. **`RESULTS` (and therefore `--digest`'s hash) is a mutable
   process-global populated as tests run, and a test method that raises
   before calling `record()` leaves no entry for that case.** Every test in
   this suite goes through `record()` en route to its assertions except a
   handful of pure-computation tests (e.g.
   `test_normalize_only_strips_the_repo_root_prefix`,
   `test_generator_round_trips_cleanly`) that call no subprocess at all and
   were never meant to contribute a case. That is by design, not an
   oversight -- but it does mean `expected_results.json`'s case count (106,
   see below) is smaller than the test count (122): several tests call the
   same helper (and therefore the same `record()` key) more than once
   within one test method (e.g. every `*_byte_identical_across_two_runs`
   test runs the same case twice, overwriting one `RESULTS` entry with the
   second, identical run rather than producing two), and the CLI-shape /
   `-h` / `--version` / cross-tool `subTest` tests intentionally share or
   skip case IDs. A reviewer expecting a strict 1:1 test-to-case mapping in
   `expected_results.json` should not assume it; it is a **case-id-keyed**
   snapshot, not a per-test-method one.

Weighted most heavily: **#1, the ReDoS timing assertion.** It is the only
limitation here that could, in principle, flip a currently-passing test to
green for the wrong reason (environment got faster) or red for the wrong
reason (environment got slower/loaded) without any change to the tool under
test. The other three are coverage gaps or documented scope boundaries, not
sources of a false verdict on an unchanged tool.
